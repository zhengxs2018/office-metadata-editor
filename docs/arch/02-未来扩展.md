# 基于现有架构的未来扩展

本文不臆造新架构，而是从 `00`/`01` 描述的真实结构上，指出**哪些能力可以低成本嫁接、哪些需要动骨架**，并标注每项扩展对现有契约的影响面。

---

## 扩展 1：新增比对字段维度（低成本，已预留）

**现状**：`FIELDS` 注册表 + `rules::ALL_RULES` 是数据驱动的。新增一个比对的元数据字段，只需：

1. `FIELDS` 加一项（带 `tier` 与 `extract` 闭包）—— 差异投影自动覆盖
2. 若它要参与风险判定，在 `ALL_RULES` 加一条 `RuleMeta`（id/权重/max_level），并在 `evaluate` 里写匹配逻辑 + `raw_field`/`field_label` 加映射
3. 配置中心 `engine.compare.*` 加对应停用词段

**影响面**：内核纯函数内部，前端 `CompareResult` 结构（FieldDiff 已按 fieldKey 泛型承载）与 IPC 契约**不变**。前端 selectors / 组件按 fieldKey 渲染，天然兼容。

**注意点**：`CompareFileInput` 是前端→内核的唯一契约。新字段必须先在 `toCompareInputs` 里从 `LoadedDocument` 投影出来，否则内核拿不到。这是唯一需要前后端同步改动的点。

---

## 扩展 2：规则引擎化（中成本，消除硬编码）

**现状**：8 条规则硬编码在 `rules.rs`，但已具备「权重 / max_level / kind / 启用开关 / 级别覆盖」的结构化元数据，且 `evaluate` 已是「遍历规则 × 两两文档」的模板。

**演进方向**：把规则定义外移到配置中心（或独立规则文件），运行时由 `install_dictionaries` 同机制装载。每条规则描述「比较哪两个字段 + 用哪种匹配器 + 权重 + 上限」。

**收益**：

- 业务可在设置页增删规则，无需改 Rust 编译
- 算法与策略分离，测试只需换配置

**风险与代价**：

- 匹配器（如 `check_person_match` 的六级降级）是规则的核心智力，外移需定义匹配器 DSL 或注册表，否则会变成「只能加简单相等规则」
- 一旦规则可热配，**可复现性**要重新约束（建议规则集哈希随 `CompareResult` 一起返回，便于审计溯源）

---

## 扩展 3：增量对比与基线追踪（中成本，动数据流）

**现状**：每次 `compare_metadata` 都是全量 `O(N²)` 两两比对，无状态。

**演进方向**：

- **基线**：把某次 `CompareResult` 存为「基线」，后续对比只报「相对基线的新增线索」，让「持续监控一批公司文档是否出现串标迹象」成为可能
- **增量**：文件数从 N 增到 N+1 时，只比对新增文档与已有文档（N 次而非 (N+1)² 次）

**影响面**：需要在 `CompareOptions` 或新命令里带入「基线 / 历史指纹」。内核接口可保持 `run_compare` 不变，由外层编排「取差集 → 调 run_compare → 与基线 diff」。

**复用点**：`normalize` 的人名指纹、时间桶 key 已经能稳定标识「同一实体」，是做基线匹配的基础，无需重造。

---

## 扩展 4：大规模批量的并发与分片（低成本，内核天然可并行）

**现状**：`run_compare` 纯函数、无共享可变状态。两两循环是主成本。

**演进方向**：把「(i,j) 文档对」分片，用 Rayon 或线程池并行跑 `evaluate` 的单对逻辑，最后合并 `aggregate`。对齐/差异阶段也可按组并行。

**约束**：`DICTIONARIES` 用 `OnceLock` 保证只读一致，并行读安全；`aggregate` 的 `BTreeMap` 需要换成线程安全聚合或各分片独立聚合后再合并。

**收益**：文档数上百时线性加速，且不改变输入/输出契约。

---

## 扩展 5：多窗口 / 多文档并行作业（中成本，动状态层）

**现状**：UI 状态收敛在 `FileContext` + `MetadataContext`（React 组件级），导出的 `LoadedDocument` 在内存。

**演进方向**：

- **多窗口**：比对作业可在独立窗口跑，结果集跨窗口共享。需把 `LoadedDocument` 与 `CompareResult` 提到进程级 store（如 Tauri 的 `State` 或前端全局），并定义「作业 id → 结果」映射
- **后台作业**：长对比走事件流（`emit` 进度），前端用 `listen` 接收，避免阻塞 UI 线程

**影响面**：前端状态层从「组件级 Context」升级为「进程级单例 + 投影」。当前架构的双 Context 派生模型已经是单实例，升级时只需在其上挂一层作业管理器，不破坏派生关系。

---

## 扩展 6：配置 Schema 化与自动 UI（低成本，已有基础）

**现状**：配置中心点分键 + `engine.compare.*` 命名空间已落地，`STOP_WORD_DICTS` 自带「配置键 ↔ 展示名 ↔ 作用域」元信息。

**演进方向**：基于元信息自动生成设置页表单（每种字典一段输入框），无需手写 UI。前端 `getConfiguration(prefix)` 已实现 vscode 风格 API，天然适配。

**复用点**：`STOP_WORD_DICTS` 的 `StopWordDictMeta` 已经是「配置即文档」的雏形，扩展新词典时元数据与 UI 同步长出。

---

## 扩展 7：新文件格式接入（中成本，资源层多态已铺垫）

**现状**：前端资源层按文件类型多态解析出 `LoadedDocument`（docx/xlsx/pdf/doc），内核只消费拍平后的 `CompareFileInput`，**不感知格式**。

**演进方向**：新增格式（如 `pptx`、WPS `et`/`wps`）只需在资源层加一个解析策略，产出相同结构的 `LoadedDocument.metadata`。内核、IPC、UI **完全不动**。

**约束**：新格式必须能提取出 `documentProperties` / `appProperties` / 痕迹作者三类字段，否则对齐与风险阶段拿不到对应值（但不报错，只是该维度缺失）。

---

## 扩展总览

| 扩展 | 成本 | 需改契约？ | 改动集中在 |
|------|------|-----------|-----------|
| 1 新比对字段 | 低 | 否（仅 CompareFileInput 加字段） | 内核 + 前端投影 |
| 2 规则引擎化 | 中 | 否（输出结构不变） | 规则定义外移 |
| 3 增量/基线 | 中 | 否（外层编排） | 新命令/选项 |
| 4 并发分片 | 低 | 否 | 内核内部并行 |
| 5 多窗口作业 | 中 | 部分（状态层升级） | 前端状态层 |
| 6 配置 Schema UI | 低 | 否 | 设置页生成 |
| 7 新文件格式 | 中 | 否 | 资源层策略 |

**结论**：当前架构的「前端投影 → IPC 最小契约 → 纯函数内核 → 结果即视图就绪」结构，使大多数扩展**不破坏 IPC 契约、不重造算法**，只在单侧加能力。真正需要动骨架的只有「多窗口状态升级」与「规则引擎化时的可复现性约束」。
