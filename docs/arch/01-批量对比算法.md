# 批量对比算法：四阶段内核详解

批量对比的内核是 `run_compare`，一个**纯函数**：输入 `CompareFileInput[]`（已解析的语义字段）+ `CompareOptions`，输出 `CompareResult`。它不读文件、不写磁盘、不访问全局可变状态，因此可被集成测试直接驱动。

本文拆解四个阶段：**对齐 → 差异 → 风险 → 归一化（工具层）**。

---

## 阶段 1：对齐（align::align_files）

**问题**：用户拖进来的文件，文件名往往是 `A公司_投标书.docx`、`B公司_投标书.docx`、`A公司_报价.docx`。内核要把「描述同一标的」的多份文档归到一个组里，才有可能横向比。

**做法**：两级匹配，按顺序尝试，命中即入组：

1. **同组优先**：若两份文档已经显式属于同一对比组（前端在 `LoadedDocument` 上标注），直接合并。
2. **文件名相似匹配**：对文件名做归一化（去扩展名、去停用词、转小写）后，相似度超过阈值则归为一组。这一步让 `A公司_投标书` 与 `B公司_投标书` 落到同一组，尽管公司名不同。
3. **标题匹配**：若文件名无法对齐，再用 `title` 字段归一化后比对兜底。

未命中任何规则的文档进入 `unmatched` 列表——**不强制归组**，而是交给用户人工判断来源。这是合规上的保守设计：宁可漏归也不错归，避免把无关文件当成「同一投标」横比而产出误导性结论。

**输出**：`AlignedGroup[]`（每组持有一个 `BTreeMap<companyId, 文件下标>`）+ `unmatched: Vec<CompareFileInput>`。用 `companyId` 作 key，天然保证「一组内每家公司最多一份代表文档」，为后续差异投影提供规整结构。

---

## 阶段 2：差异投影（diff::diff_group）

**问题**：给定一组「同一标的」的文档（可能跨多家公司），逐字段判断它们取值是否一致。

**做法**：遍历 `FIELDS` 注册表（约 20 个参与比对的字段，每个带 `tier` 与 `extract` 闭包）。对每个字段：

1. 用 `extract` 从每份成员文档取原始值，`.trim()` 后归一化（`normalize`），空值记为 `is_empty`
2. 按「在场情况」判定 `DiffState`：
   - **全部为空** → `Ignored`（无信息，不参与风险）
   - **部分为空** → `Missing`（有公司填了、有公司没填——缺失本身可能是疑点）
   - **全部非空** → 比较归一化后的键：
     - 全相等 → `Identical`
     - 两两最小相似度 ≥ 0.85 → `Similar`（表述不同但大概率同一事实，如「北京市」vs「北京」）
     - 否则 → `Conflict`（取值实质不同）

**关键设计**：`Identical`（取值一致）**只描述事实，不代表安全**。在跨公司横向对比里，「风险字段取值完全一致」恰恰可能是疑点（疑似套用同一模板/同一人制作）。所以差异状态机只负责「事实分类」，风险级别由阶段 3 单独给出。职责切分干净。

对 `tier == Ignored` 的字段直接跳过，不在结果里出现。

**输出**：每组的 `FieldDiff[]`，每个 `FieldDiff` 携带 `fieldKey` / `tier` / `state` / 各公司 `FieldValue`（raw + normalized）。

## 阶段 3：风险判定（rules::evaluate）

**这是算法的核心**。它回答：「两家不同公司的文档之间，是否存在「疑似同一主体 / 同一出处」的证据？」

### 3.1 两两比对骨架

对所有文档做双重循环 `for i < j`，**跳过同公司配对**（自己比自己无意义），对每对不同公司的文档 `(a, b)` 跑 8 条规则。

### 3.2 八条规则（证据类型分两类）

**SameEntity（疑似同一主体）**

| 规则 ID | 比较字段 | 权重 | 强度上限 |
|---------|---------|------|---------|
| `SAME_PERSON` | creator / lastModifiedBy | 50 | High |
| `SAME_MANAGER` | manager | 40 | High |
| `SAME_APP_COMPANY` | appCompany（完全一致） | 35 | High |
| `SIMILAR_APP_COMPANY` | appCompany（编辑距离相似 ≥0.7） | 20 | Medium |
| `REVISION_TRACES` | 批注/修订/ XMP 作者集合交集 | 40 | Medium |

**SameOrigin（疑似同一出处）**

| 规则 ID | 比较字段 | 权重 | 强度上限 |
|---------|---------|------|---------|
| `SAME_TEMPLATE` | template（非通用模板完全一致） | 30 | High |
| `CLOSE_TIMESTAMP` | created（时间窗口内接近） | 25 | Medium |
| `SAME_APP_FINGERPRINT` | application + appVersion | 5 | **Low（恒弱）** |

**强度上限（max_level）** 的意义：一条弱信号（如软件版本相同）即使所属公司对整体被其他规则抬到 high，这条线索自身的展示级别也不会超过 Low，避免「蹭强度」。

### 3.3 人名匹配（check_person_match）—— 最精密的部分

判定两人名是否「同一人」不是简单相等，而是一串降级匹配：

1. **EXACT**：归一化后完全相同 → 置信 1.0
2. **NAME_ANAGRAM**：中文姓名**乱序/带空格**视为同一人（「卓栋 高」vs「高卓栋」）。做法：把字符多重集排序生成指纹 + 转拼音，再比较。→ 0.92
3. **PINYIN_EDIT**：编辑距离 ≤1 且拼音相同（如错别字「张山」vs「张三」）→ 0.95
4. **ANAGRAM_ANCHORED**：≤3 字姓名，首/尾字锚定 + 字符集相同 → 0.90
5. **EDIT_SIM**：编辑距离相似度 ≥0.8 → 用相似度
6. **SUBSET_NORM / SUBSET_PINYIN**：一方是另一方的子集（含拼音子集，如「张」⊂「张三」）→ 0.88 / 0.85

返回 `(置信度, 算法标签, 实体键)`。实体键用于把不同写法归并到同一人（如两个人名都指向 `zhang|san`）。**通用账户名（来自 `genericAuthors` 停用词）不具鉴别力，在痕迹交叉时被排除**。

### 3.4 证据链聚合（aggregate）—— 多规则交叉才升级

单条规则命中只产出 `RiskFinding`。真正决定「这对公司风险有多高」的是**聚合**：

```
对每个 finding，按 (companyA, companyB) 累加：
  score += weight × finding.score        // weight 是规则权重，finding.score 是匹配置信度
  rules.insert(rule_id)                  // 记录命中了哪些「不同类」规则

聚合后判定公司对级别：
  score ≥ 70 且 命中规则种类 ≥ 2  → High
  score ≥ 35                         → Medium
  否则                               → Low
```

**关键阈值设计**：

- **High 要求「≥2 类不同规则交叉」**。单一规则（哪怕权重 50 的 `SAME_PERSON`）只能把分数推到 50，不够 70 的 High 线；必须有第二类证据（如同时模板相同）才能跨线。这直接落实「单一线索不定性」，符合招投标合规用语约束（只用「疑似 / 线索」，不认定）。
- 聚合完成后，**回写每条 finding 的 `level`**：取「公司对级别」与「规则自身 max_level」的较小值，使弱信号线索不会因同组其他强证据而被错误提升。

### 3.5 输出

- `RiskFinding[]`：扁平线索，每条带 `ruleId` / `level` / `evidence_kind` / `refs`（两条证据引用：哪家公司、哪个文档、哪个字段、原始值）/ `explain`（人话解释）
- `CompanyPairRisk[]`：按公司对聚合，含 `level` / `pair_score` / 命中规则数 / 线索 id 列表，按级别→分数排序。前端摘要区直接消费它。

## 阶段 4：归一化（normalize::*）—— 贯穿前三阶段的工具层

归一化不是独立阶段，而是被对齐、差异、风险三处调用。它解决「同名不同写」问题：

- **`normalize(text)`**：小写、去标点空白、命中字段停用词则返回 `None`（视为无信息）。让「Office」「办公软件」这类噪声词不进入比对。
- **`name_fingerprint(s)`**：把人名转成**与顺序/空格无关**的指纹——字符排序 + 转拼音。这是乱序匹配的基础。
- **`similarity(a, b)`**：基于 Levenshtein 编辑距离的相似度 `1 - dist/maxLen`，用于公司标识相似、字段相似判定。
- **`parse_timestamp` / `timestamp_bucket_key`**：无依赖解析 ISO 时间串，把两个接近的创建时间归到同一「时间桶」，用于 `CLOSE_TIMESTAMP` 的接近判定（如 30 分钟内视为同批次）。
- **`normalize_template`**：只取文件名末段 + 小写，并排除通用模板白名单（如 `Normal.dotm`），让「都用默认模板」不误判为同出处。

**配置驱动**：停用词表（`fields/templateStopWords/genericAuthors` 等 5 类）不写死在代码里，而是在启动时由 `install_dictionaries` 从配置中心 `engine.compare.*` 装载一次（`OnceLock`），进程内保持一致，保证结果可复现。用户可在设置页覆盖。

---

## 配置如何影响算法（CompareOptions）

`CompareOptions` 控制算法行为，且可在运行时由设置页调整：

- `rule_enabled(id)`：某条规则被禁用则不产出该类线索（规则产品化预留）
- `rule_level_override(id)`：单规则级别覆盖，但受 `max_level` 上限制约
- `close_timestamp_minutes()`：时间接近判定的窗口（分钟），0 表示关闭该规则
- `stop_words` / 词典：经配置中心注入，驱动归一化与模板白名单

---

## 算法复杂度与可扩展性

- 对齐：O(N²) 文件名/标题两两比对（N 为文件数，批量场景 N 不大）
- 差异：O(G×F)，G 组数、F 字段数，常量级
- 风险：O(N² × R)，R 为规则数（固定 8），双重循环是主成本。批量对比本质是「跨公司两两全比对」，规模受业务约束（一次对比通常数十份），无需分布式

**新增一条比对维度**的成本：在 `FIELDS` 或 `ALL_RULES` 加一项 + 配置中心加一段停用词 + `field_label`/`raw_field` 映射，内核其余不动。这是该算法「数据驱动、规则可插拔」带来的实际收益。
