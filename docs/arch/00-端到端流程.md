# 批量对比：从前端到后端的完整流程

本文描述一次「批量对比」操作在客户端程序内如何穿层流动。**不讲设计模式名词**，只讲真实的数据与控制流。

## 0. 一句话链路

```
用户点击「开始对比」
  → ComparePage.handleRun
  → toCompareInputs(已解析文档 → CompareFileInput[])
  → invoke('compare_metadata', { files })          [IPC 信任边界]
  → Rust 命令 compare_metadata
  → run_compare(files, options)                    [四阶段内核]
      1. align   对齐分组
      2. diff    组内字段差异投影
      3. rules   跨组两两风险评分
      4. normalize 已并入前序阶段
  → CompareResult(JSON) 回程
  → setResult(next) → selectors 投影 → UI 渲染 / 导出 Excel
```

## 1. 触发前：数据从哪来

对比的输入不是文件本身，而是**已经在前端解析好的文档**。链路上游：

- 用户在前端拖入文件 → `FileContext` 登记文件与所属公司（`companyId`）
- `MetadataContext` 监听文件变化，对每个 `ready` 文档调用资源层解析，产出 `LoadedDocument`
- `LoadedDocument.metadata` 里已经提取出 `documentProperties`（作者/创建时间/标题等）与 `appProperties`（公司标识/模板/软件版本等），以及隐藏痕迹作者集合（`annotationAuthors` / `revisionAuthors` / `xmpCreators`）

**关键事实**：比对内核**不读文件、不碰磁盘**。它只消费前端已经物化的结构化字段。这把「格式解析的复杂度」隔离在前端资源层，内核保持纯计算。

## 2. 前端投影：LoadedDocument → CompareFileInput

`compare-page/index.tsx` 的 `toCompareInputs()` 做字段裁剪与搬运：

```ts
function toCompareInputs(documents, companyById): CompareFileInput[] {
  return documents
    .filter(doc => doc.status === 'ready' && doc.companyId)   // 仅取就绪且已归属公司的
    .map(doc => {
      const props = doc.metadata.documentProperties;
      const app   = doc.metadata.appProperties;
      const company = companyById[doc.companyId];
      return {
        id, companyId, companyName, fileName,
        creator:            text(props?.creator),
        lastModifiedBy:     text(props?.lastModifiedBy),
        appCompany:         text(app?.company),
        manager:            text(app?.manager),
        template:           text(app?.template),
        application:        text(app?.application),
        appVersion:         text(app?.appVersion),
        created:            text(props?.created),
        modified:           text(props?.modified),
        revision:           text(props?.revision),
        // ... 其余 9 个分类字段
        annotationAuthors:  doc.metadata.annotationAuthors ?? [],
        revisionAuthors:    doc.metadata.revisionAuthors  ?? [],
        xmpCreators:        doc.metadata.xmpCreators      ?? [],
        hasHiddenMarkers:   doc.metadata.hasHiddenMarkers ?? false,
      };
    });
}
```

投影的本质：**把 20 个分散在前端模型里的字段，拍平成一个「比对专用视图」**。`text()` 统一处理 `undefined` → `''`，保证 IPC 传输的是规整字符串。`CompareFileInput` 是前端与内核之间的**唯一契约类型**——它不携带文件路径、不携带原始 OOXML 节点，只携带内核需要的语义字段。

## 3. IPC 边界：invoke 发出什么

```ts
const files = toCompareInputs(documents, companyById);
const next = await invoke<CompareResult>('compare_metadata', { files });
```

- 命令名 `compare_metadata` 与 Rust 侧 `#[tauri::command] fn compare_metadata` **严格一致**（契约红线）
- 入参是一个 JSON 数组 `files: CompareFileInput[]`，无 `options` 时后端用 `Option::unwrap_or_default()`
- 返回 `CompareResult`（JSON），前端用 `invoke<CompareResult>` 显式标注返回类型

**信任边界**：前端只提交「已经解析好的语义字段」，不提交文件路径、不提交二进制。内核因此无法被诱导去读任意磁盘文件——这是 Tauri 安全模型在该程序里的具体落地。

## 4. 内核入口：命令 → run_compare

```rust
#[tauri::command]
fn compare_metadata(
    files: Vec<CompareFileInput>,
    options: Option<CompareOptions>,
) -> CompareResult {
    documents::compare::run_compare(&files, &options.unwrap_or_default())
}
```

命令层**只做参数透传 + 默认值兜底**，零业务逻辑。所有算法在 `documents::compare::run_compare` 内。

## 5. 四阶段内核（run_compare）

`run_compare` 是纯函数：**输入 `CompareFileInput[]` + `CompareOptions`，输出 `CompareResult`，无副作用、不碰 IO**。四个阶段：

| 阶段 | 函数 | 输入 | 输出 | 作用 |
|------|------|------|------|------|
| 1 对齐 | `align::align_files` | 全部文件 | `AlignedGroup[]` + `unmatched` | 按文件名/标题/公司把多份文档归到「同一标的」 |
| 2 差异 | `diff::diff_group`（对每个组） | 组内成员 | `FieldDiff[]` | 逐字段判定 identical/similar/conflict/missing |
| 3 风险 | `rules::evaluate`（跨组两两） | 全部文件 | `RiskFinding[]` + `CompanyPairRisk[]` | 8 条规则打点，按公司对聚合评分 |
| 4 归一化 | `normalize::*` | —— | —— | 被阶段 1/2/3 调用，提供人名指纹/编辑距离/时间分桶 |

阶段 4 不是独立一遍，而是**贯穿在前三阶段内部的工具层**（人名乱序匹配、公司标识相似度、时间接近判定都要用到归一化）。详见 `01-批量对比算法.md`。

## 6. 回程：CompareResult 的结构

`CompareResult` 是一个「已经可以渲染」的结果树，不是原始中间数据：

- `companies`: 参与公司快照（`companyId` / `companyName`）
- `groups`: 对齐组数组，每组含 `cells`（公司→文档映射）+ `diffs`（`FieldDiff[]`）+ `riskLevel` / `riskSummary`
- `unmatched`: 未归入任何组的文件（需人工复核来源）
- `findings`: 扁平的跨公司风险线索（`RiskFinding[]`），每条带 `ruleId` / `level` / `refs`（两条证据引用）
- `companyRisks`: 按公司对聚合的风险（`CompanyPairRisk[]`，high/medium/low + 命中规则数 + 合计分）
- `stats`: 公司数 / 文件数 / 组数 / 各类线索计数

**设计要点**：内核把「对齐、差异、风险」三种视图全部算好再一次性返回。前端不需要、也不应该再跑一遍算法——它只做**展示投影**（`selectors.ts` 的过滤/排序/折叠），不重新计算事实。

## 7. 前端投影：CompareResult → 视图

`compare-page` 拿到 `CompareResult` 后：

- `selectors.ts`：纯函数，负责`过滤`（risky/different/missing）、`排序`（risk/diffCount/confidence）、`折叠低危`、`按字段筛选`、`按关键字搜索`。**只搬运与重组，不新增事实**
- 组件树消费投影结果：`compare-workbench`（总装）→ `alignment-matrix`（对齐矩阵）→ `field-diff-panel`（字段差异）→ `findings-list`（线索清单，可展开证据来源）→ `compare-summary`（风险摘要）

## 8. 导出：结果树 → Excel

`lib/documents/compare/export.ts` 直接消费 `CompareResult` 生成 xlsx 工作簿（概览 / 对齐明细 / 字段差异 / 风险线索四表），经 Tauri `write_binary_file` + base64 落盘。导出是**读取结果树**而非重新计算，与内核解耦。

## 9. 完整时序（单线程视角）

```
[UI] 点击「开始对比」
  │ canRun = 公司数≥2 且未在对比中
  ▼
[ComparePage.handleRun]
  │ toCompareInputs(documents, companyById)  → CompareFileInput[]
  │ setComparing(true)
  ▼
[Tauri invoke]  'compare_metadata' { files }
  │  ────────────── IPC 信任边界（只传语义字段，不传路径/二进制）──────────────
  ▼
[Rust compare_metadata]  参数透传 + 默认值兜底
  ▼
[run_compare]  纯函数
  ├─ align::align_files        → groups + unmatched
  ├─ diff::diff_group ×N组     → FieldDiff[]
  ├─ rules::evaluate           → findings + companyRisks
  └─ normalize::*  （被上述三阶段调用）
  ▼
[CompareResult]  (JSON 序列化)
  │  ──────────────────────── IPC 回程 ───────────────────────
  ▼
[ComparePage]  setResult(next); setComparing(false)
  ▼
[selectors]  过滤/排序/折叠
  ▼
[组件树]  渲染  +  [export.ts] 导出 Excel
```

## 10. 该流程暴露的架构事实（非模式名词）

- **内核是纯函数**：`run_compare` 无 IO、无全局可变状态，可单测。集成测试 `src-tauri/tests/*.rs` 直接调它，不经 Tauri 运行时。
- **IPC 是最小契约面**：一个命令、一个入参类型、一个返回类型。前端不感知内核如何分阶段。
- **解析与计算分离**：文件解析（含 OOXML/PDF 差异）在前端资源层，语义比对在 Rust 内核。两侧通过 `CompareFileInput` 这一种拍平结构交接。
- **结果即视图就绪**：内核交付的是「可渲染树」，前端只做展示投影与导出，不重复算法。这正是「前端瘦、后端重」在该程序里的具体含义。
